# NorthStar Churn Model Security and Privacy Assessment

## Task 3a: STRIDE threat model

| Threat | STRIDE category | Likelihood | Impact | Mitigation | AWS control |
|---|---|---:|---:|---|---|
| An attacker or unauthorized workload invokes the churn endpoint under another service's identity. | Spoofing | Medium | High | Require authenticated, signed requests and grant invocation only to the campaign workload role. Alert on calls from unexpected principals. | IAM `sagemaker:InvokeEndpoint` least-privilege policy, AWS STS/SigV4 authentication, and CloudTrail identity records. |

| A malicious model artifact is substituted between training and deployment. | Tampering | Low | High | Deploy only the exact package ARN emitted by the successful pipeline, require manual approval, and retain immutable package/version evidence. | SageMaker Model Registry approval state, CodePipeline Manual Approval, S3 Versioning, and IAM restrictions on `UpdateModelPackage`/`CreateModel`. |

The current wildcard SageMaker resource grant is a gap requiring tightening. |

## Task 3b: Data classification

The table states the required standard. The current shared data bucket defaults to SSE-S3; therefore rows requiring SSE-KMS or CSE identify remediation that must occur before production. SSE-S3 is sufficient only where confidentiality and key-level audit requirements are low. SSE-KMS is selected for customer-linked or proprietary data because it provides a separately controlled key, key policy, revocation, and CloudTrail usage evidence. CSE protects direct identifiers before they reach AWS.

| Asset | Tier | Encryption standard and reason | IAM access policy | Third-party sharing |
|---|---|---|---|---|
| Customer PII | Restricted | **CSE** for direct identifiers; store only tokenized customer ID and hashed email in AWS. This separates identity keys from the platform. | Privacy-approved ingestion role only; DataEngineer may process tokenized records; deny MLEngineer and ModelMonitor direct identifiers. | No, except a contracted processor with DPA, purpose limitation, and approved key exchange. |
| Transaction history | Confidential | **SSE-KMS** because purchases are customer-linked and commercially sensitive. | DataEngineer read/write on raw and processed prefixes; MLEngineer receives derived features only. | Only aggregated/de-identified extracts under contract. |
| Behavioral clickstream | Restricted | **SSE-KMS** because event sequences and free-text searches can contain identifiers or sensitive intent. | Dedicated ingestion/DataEngineer access; mask `search_query`; no routine MLEngineer access. | No raw sharing; only privacy-reviewed aggregates. |
| Product catalog | Public | **SSE-S3** because catalog descriptions and public prices are non-sensitive; S3-managed encryption is adequate at rest. | Readable by platform roles; writes limited to catalog ingestion role. | Yes, after confirming no internal cost or embargoed fields. |
| Model weights | Confidential | **SSE-KMS** to protect NorthStar IP and provide audited decrypt permission for training/serving roles. | MLEngineer and SageMaker execution role; ModelMonitor read only when required; no DataEngineer write access. | Only under model licensing, security review, and an approved processor agreement. |
| Inference logs/data capture | Restricted | **SSE-KMS** because feature vectors, predictions, timestamps, and request metadata may be linkable to customers. | SageMaker execution role writes; ModelMonitor receives read-only access; analysts use approved, de-identified views. | No raw sharing; de-identified incident extracts only. |
| Feature Store records | Restricted | **SSE-KMS** because per-customer identifiers and behavioral aggregates enable profiling. | DataEngineer ingests; MLEngineer reads approved features; ModelMonitor reads only monitoring fields. | No row-level sharing; aggregate statistics require privacy approval. |

## Task 4: Privacy impact assessment

### 1. Personal data inventory

In ingestion, raw customer and transaction files contain tokenized `customer_id`, hashed email, age band, loyalty attributes, purchase dates, amounts, channel, and product/category history. Clickstream ingestion may contain customer/session IDs, page events, referral source, and risky free-text searches. Glue processing joins customer-linked transactions and creates recency, frequency, spend, value, basket, diversity, and online/store-ratio features. Feature Store retains these aggregates with `customer_id` and event time. Training consumes the aggregates, loyalty-tier slice, and churn label; the XGBoost artifact encodes statistical influence rather than readable customer rows. Inference processes the eleven numeric features and produces a churn score. SageMaker data capture stores request features, prediction output, endpoint/variant, and timestamps in S3.

### 2. Lawful basis

Use **legitimate interests** under GDPR Article 6(1)(f). NorthStar has a specific commercial interest in identifying likely churn among existing customers so it can send relevant retention outreach, and purchase history is directly related to that existing relationship. Contractual necessity is too broad because churn prediction is not required to complete a sale, and consent is fragile for a core analytical process and may not be freely given when tied to loyalty benefits. NorthStar must document a legitimate-interest balancing test, give clear notice, honor marketing objections, avoid sensitive/protected attributes, restrict scores to retention use, and provide human review for consequential actions. The limited feature set, access controls, short inference-log retention, and opt-out mechanism reduce customer impact.

### 3. Data minimization

Training uses only aggregate behavioral features listed in `FEATURE_COLUMNS`. Raw name, postal address, telephone, unhashed email, payment method/account data, precise location, full product descriptions, free-text search queries, device identifiers, and customer-service message content were considered unnecessary and excluded. Age band, gender, ethnicity, disability, and other protected or proxy attributes are excluded from model inputs; loyalty tier is retained only for evaluation slices, not as a training feature. `customer_id` is required to join and erase records but is removed before the XGBoost matrix is built.

### 4. Right-to-erasure workflow: `C00123456`

1. **Raw S3 data:** authenticate the request, place the ID on a suppression list, locate affected customer/transaction/clickstream objects with Glue/Athena, rewrite each object without `C00123456`, and delete every superseded S3 object version and delete marker. Re-run the query and require zero rows.
2. **Feature Store:** call Feature Store `DeleteRecord` for the record identifier in the **online store** and verify it is no longer returned. The **offline store is append-only history in S3**; run a purge job that rewrites affected partitions without the ID, removes old object versions, updates the Glue catalog if paths change, and verifies zero Athena results. Keep a non-identifying deletion audit record.
3. **Training data and model:** delete derived feature snapshots/evaluation rows containing the ID, regenerate training data from purged sources, and retrain/register a replacement model. Reject and retire packages trained on the old snapshot according to the retention policy. There is no supported operation that subtracts one person's influence from an existing XGBoost artifact.
4. **Inference logs:** use the request/customer correlation record to locate captured S3 objects, rewrite mixed objects without matching events, delete all old versions, and verify with Athena/S3 Inventory. Remove correlated CloudWatch application logs while retaining a minimal non-personal compliance audit.

The **trained model is the hardest step**: a customer's contribution is distributed across tree splits and cannot be found or deleted as a row. Effective erasure requires purging upstream/offline history and retraining; the append-only offline Feature Store and versioned capture objects make that process operationally expensive and require explicit verification.
